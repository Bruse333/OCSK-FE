# 故障排查流程构建器 — 设计方案

> 版本：v1.2（P2 已完成，含 PC/H5 流程模式 + 孤儿文件清理）  
> 日期：2026-08-04

---

## 1. 可行性结论

**完全可以实现**，且与现有系统天然契合：

- 现有的排查记录（trbsts）是"图文答案"，流程构建器是"引导式问答路径"，两者是同一知识的两种呈现形态；
- 技术栈无需大改：Vue 3 + Element Plus 足够支撑。画布部分推荐引入 **@vue-flow/core**（Vue 3 原生的节点流程图库，提供拖拽、缩放、连线、吸附等开箱能力，体积小、MIT 协议）；若不想加依赖，也可以自研 SVG + Pointer Events 的轻量画布（节点类型只有 4 种，工作量可控）；
- 存储用 **JSON 文件导入导出** 即可先跑通（零后端改动），后续再平滑迁移到后端持久化。

## 3. 页面设计

### 3.1 流程构建器（PC 优先，新增路由 `/system/flow-builder`）

布局分为四个区域：

```
┌──────────────────────────────────────────────────────────┐
│ 顶部工具栏：流程名称 | 保存 校验 预览 导出JSON 导入JSON   │
├──────────┬───────────────────────────────┬───────────────┤
│ 左侧组件面板 │        中央画布              │ 右侧属性面板   │
│ ┌──────┐ │  （网格背景 + 缩放/平移）      │ 选中节点时：   │
│ │开始节点│ │   ┌──┐                       │ - 类型图标     │
│ └──────┘ │   │起├──┐                     │ - 标题         │
│ ┌──────┐ │   └──┘  │  ┌────┐             │ - 详细说明     │
│ │步骤节点│ │         └─▶│步骤│──▶ ◇判断    │ - 图片/文档    │
│ └──────┘ │            └────┘     ├─是─▶…  │ - 分支选项(判断)│
│ ┌──────┐ │                       └─否─▶…  │               │
│ │判断节点│ │   （拖拽组件到画布创建节点）    │ 未选中时显示   │
│ └──────┘ │   （拖出连线建立跳转）          │ 流程基本信息   │
│ ┌──────┐ │                               │ (船型/描述等)  │
│ │结束节点│ │                               │               │
│ └──────┘ │                               │               │
└──────────┴───────────────────────────────┴───────────────┘
```

### 3.2 节点类型（4 种，够用且不冗余）

| 节点          | 语义              | 出口      | 内容字段                        |
| ----------- | --------------- | ------- | --------------------------- |
| 开始 start    | 流程入口，**有且仅有一个** | 1 条出边   | 标题、初始现象描述                   |
| 步骤 step     | 一个具体操作/检查动作     | 1 条出边   | 标题、详细说明、图片[]、文档[]           |
| 判断 decision | 向用户提问，按结果分支     | 2~N 条出边 | 问题、选项列表[{label, target}]    |
| 结束 end      | 流程终点，给出结论       | 无出边     | 结论类型（已解决/未解决需转厂家）、结论文本、建议措施 |

> 设计要点：判断节点的"选项"既是数据也是连线锚点。例如"电源指示灯是否亮起？"→ 选项【亮 / 不亮】分别连向不同后续节点。这是引导式排查的核心交互。

### 3.3 构建器交互逻辑

1. **创建节点**：从左侧组件面板拖入画布（或单击追加到画布中心）；
2. **连线**：从节点右侧锚点拖出连线到目标节点；判断节点每个选项一个锚点，锚点上直接显示选项文字；
3. **编辑**：点击节点 → 右侧属性面板编辑标题/说明/选项/上传图片文档（复用现有 `POST /upload`，限制沿用：图片≤9张<2M，文档 pdf/doc/docx <2M）；
4. **删除**：选中节点/连线按 Delete 或右键菜单；开始节点不可删除；
5. **校验**（保存/导出前自动执行）：
   - 必须恰好 1 个开始节点、至少 1 个结束节点；
   - 从开始节点出发必须能到达所有节点（不允许孤儿节点）；
   - 判断节点 ≥2 个选项且每个选项都已连线；
   - 步骤/开始节点有且仅有 1 条出边；
   - 不允许悬空连线（目标必须存在）；
   - 允许回边（循环），例如"仍未解决 → 回到检查步骤 A"，但要提示防死循环；
6. **预览**：构建器内一键进入"模拟运行"，以使用者视角走一遍流程；
7. **保存/导出**：导出单个 `.json` 文件（Blob 下载，文件名 `flow_{名称}_{yyyyMMdd}.json`）；导入时做 schema 校验 + version 兼容检查，并可选择重新生成所有节点 id 防冲突。

### 3.4 检索页详情 — "流程模式"（Runner）

- 检索详情弹窗顶部加 Tab：**图文模式 | 流程模式**（该记录绑定了流程时才显示流程 Tab）；
- 流程模式是一个"向导式播放器"，不需要画布：
  - 当前节点卡片：标题 + 详细说明 + 图片轮播/文档下载；
  - 判断节点：选项渲染成大按钮（如【正常】【异常】）；
  - 步骤节点：底部【已完成，下一步】；
  - 结束节点：展示结论 + 【重新排查】按钮；
  - 顶部面包屑/进度条显示已走路径，支持【上一步】回退（历史栈）；
- H5 端同样只做 Runner（移动端不建模、只引导），交互天然适配手机。

## 4. 核心：流程数据结构（JSON Schema）

### 4.1 顶层结构

```json
{
  "version": "1.0.0",
  "id": "flow_8f3a2c1d9e",
  "name": "发动机无法启动排查流程",
  "shipId": 3,
  "shipName": "Dolphin3",
  "bindTrbstId": 1024,
  "description": "适用于 Dolphin3 冷启动失败的引导排查",
  "author": "zhangsan",
  "createTime": "2026-08-04 10:00:00",
  "updateTime": "2026-08-04 10:30:00",
  "canvas": { "zoom": 1, "offsetX": 0, "offsetY": 0 },
  "nodes": [ /* 见 4.2 */ ],
  "edges": [ /* 见 4.3 */ ]
}
```

| 字段                  | 说明                            |
| ------------------- | ----------------------------- |
| `version`           | 结构版本号，导入时做兼容/迁移判断，**必须有**     |
| `id`                | 流程唯一 id（导入时可重新生成防冲突）          |
| `shipId / shipName` | 关联船型（冗余 name 便于离线查看）          |
| `bindTrbstId`       | 可选，绑定某条排查记录，检索详情据此出现"流程模式"Tab |
| `canvas`            | 画布视口状态，保证导入后"所见即所存"           |

### 4.2 节点（nodes[]）

通用字段 + 按类型的扩展字段：

```json
{
  "id": "n_start_1",
  "type": "start | step | decision | end",
  "label": "节点标题",
  "description": "详细说明（支持多行文本）",
  "position": { "x": 120, "y": 240 },
  "media": {
    "photos": ["https://oss.../a.png"],
    "docs": ["https://oss.../b.pdf"]
  },

  "question": "电源指示灯是否亮起？",
  "options": [
    { "id": "opt_1", "label": "亮" },
    { "id": "opt_2", "label": "不亮" }
  ],

  "result": {
    "resolved": true,
    "conclusion": "保险丝熔断，更换 10A 保险丝后恢复",
    "suggestion": "建议备件清单中加入该型号保险丝"
  }
}
```

- `question` + `options[]`：仅 `decision` 类型使用；选项的跳转目标**不写在节点里**，统一由 edges 表达（见下），这样节点与连线解耦，画布渲染和 Runner 走路径用同一份 edges；
- `result`：仅 `end` 类型使用，`resolved` 布尔值让统计页未来可以统计"解决率"；
- `position` 只影响画布展示，Runner 完全忽略它。

### 4.3 连线（edges[]）

```json
{
  "id": "e_12",
  "source": "n_decision_1",
  "sourceOption": "opt_2",
  "target": "n_step_5",
  "label": ""
}
```

- 普通节点出边：`source` + `target` 即可，`sourceOption` 为 null；
- 判断节点出边：必须带 `sourceOption`，Runner 根据用户点选的 option id 找到对应 edge 跳到 target；
- 结构与 Vue Flow / LogicFlow 的 edge 模型天然兼容，后续换库零成本。

### 4.4 Runner 执行模型（状态机）

```
currentId = 开始节点
history = []                        // 回退栈

loop:
  node = nodes.find(id === currentId)
  switch node.type:
    case 'start':    展示初始描述 → [开始排查] → 沿唯一出边前进
    case 'step':     展示说明/图片/文档 → [已完成，下一步] → 沿唯一出边前进
    case 'decision': 展示问题 + 选项按钮 → 用户点选 opt → 找 (source=node.id
                     且 sourceOption=opt.id) 的 edge → 跳到其 target
    case 'end':      展示结论 → [重新排查] / [返回检索]
  每次跳转前 history.push(currentId)，[上一步] = history.pop()
```

这个模型只依赖 nodes + edges，不依赖 position，因此 JSON 文件即使手工编写也能直接运行。

## 5. 存储方案（分阶段）

### 阶段一（零后端改动，先跑通）

- 流程以 JSON 文件存在用户本地，导出/导入即全部持久化；
- 与排查记录的关联：`bindTrbstId` 写在 JSON 内；检索详情页点"流程模式"时弹出"导入该记录的流程文件"。

### 阶段一·备选（推荐，零表结构改动）

- 直接把流程 JSON 作为附件通过现有 `POST /upload` 传到 OSS，得到一个 `.json` URL；
- 存进该条 trbsts 记录的 `doc[]` 数组里（约定以 `.flow.json` 结尾），详情页检测到 doc 中有 `.flow.json` 即出现"流程模式"Tab，点开直接拉取 URL 解析运行。**不需要改任何后端代码**。

### 阶段二（后端配合，终态）

- 新增表 `t_flow(id, ship_id, trbst_id, name, data(JSON), author, create_time, update_time)`；
- API：`GET /flows?trbstId=`、`PUT /flows`（新增）、`POST /flows`（更新）、`DELETE /flows?id=`；
- 导出/导入文件功能保留，作为备份与跨环境迁移手段。

## 7. 实施分期建议

| 期  | 内容                                            | 产出          |
| -- | --------------------------------------------- | ----------- |
| P1 | 数据结构定稿 + FlowBuilder PC 页（画布/属性面板/校验/导入导出/预览/提交绑定） | 可搭建、提交绑定到排查记录 |
| P2 | 检索详情"流程模式"Runner（PC + H5）+ `.flow.json` 附件约定 + 删除记录清理孤儿流程文件 | 端到端闭环       |
| P3 | 小程序端流程模式 Runner（仅播放，不建模）+ flowSchema 核心逻辑抽包复用  | 多端覆盖        |

### 7.1 P3 小程序端流程模式实现思路

小程序（微信/支付宝/抖音等）运行环境无 DOM、不能使用 Vue Flow 与 Element Plus，但流程"播放器"本质上是一个**纯状态机 + 列表渲染**，与运行环境无关。核心思路是**逻辑层复用、视图层重写**。

#### 7.1.1 可复用部分（逻辑层，零改动）

`src/utils/flowSchema.js` 中的纯函数不依赖任何 DOM/Browser API，可直接迁移到小程序：

| 函数 | 作用 | 小程序用途 |
| --- | --- | --- |
| `parseFlow(text, opts)` | 解析 + schema 校验 + version 兼容 + 自动修正 | 下载 flowUrl 后解析 |
| `validateFlow(flow, opts)` | 流程完整性校验 | 可选，加载前预检 |
| `getStartNode(flow)` | 取开始节点 | Runner 初始化 |
| `getOutEdges(flow, nodeId, optionId)` | 取出边 | start/step 前进、decision 按选项跳转 |
| `getNodeById(flow, id)` | 按 id 取节点 | 状态机取当前节点 |
| `regenerateIds(flow)` | 重生成 id | 小程序端不需要（只读不编辑） |

> 迁移方式：把上述函数抽到 `src/utils/flowCore.js`（无 Vue/无 DOM 依赖），Web 端 `flowSchema.js` re-export 或直接引用，小程序端 copy 该文件即可。这样**一份核心逻辑三端共用**，校验/解析规则升级时只改一处。

#### 7.1.2 需重写部分（视图层 + 运行时 API）

| Web 端实现 | 小程序端替换 |
| --- | --- |
| `fetch(flowUrl)` 下载 JSON | `wx.downloadFile` 或 `wx.request` 直接拉文本（OSS 需在 request 合法域名内） |
| `<el-image>` 图片预览 | `<image>` 组件 + `wx.previewImage`（支持手势缩放） |
| `<a href>` 文档下载 | `<button open-type="...">` 或 `wx.downloadFile` + `wx.openDocument` |
| Vue 响应式 data/computed | 小程序 Page data + setData，或用 Taro/uni-app 直接复用 Vue 语法 |
| `ElMessage` 提示 | `wx.showToast` / `wx.showModal` |
| DOM 事件 `@click` | `bindtap` |

#### 7.1.3 推荐技术路线（按改造成本递增）

1. **Taro / uni-app（推荐）**：现有项目是 Vue 3，用 Taro 4（Vue 3）或 uni-app（Vue 3）可**近乎原样复用** `FlowRunner.vue` 的 `<template>` 与状态机逻辑，仅把 `el-image` 换成 `<image>`、`ElMessage` 换成 `Taro.showToast`。检索页 `RetrievalH5.vue` 也可大量复用。改造成本最低。
2. **原生小程序**：把 `FlowRunner.vue` 的状态机逻辑翻译成 `flowRunner.js`（Page 或 Component），WXML 手写节点卡片/选项按钮/结论盒。逻辑层用 7.1.1 抽出的 `flowCore.js`。适合已存在原生小程序工程的情况。
3. **H5 内嵌 WebView**：把现有 H5 检索页塞进小程序 `<web-view>`，零改造，但要处理登录态透传、OSS 域名白名单。体验略逊于原生，但最快。

#### 7.1.4 数据流（与 Web 端一致）

```
小程序检索页 → GET /trbsts（后端返回 rows[i].flowUrl）
  → 点击记录 → 详情页
    → flowUrl 非空：显示「图文/流程」Tab
      → 选「流程」→ downloadFile(flowUrl) → parseFlow → 渲染 Runner
      → flowUrl 为空：仅图文
```

后端无需任何改动：`/trbsts` 列表接口已返回 `flowUrl`，小程序直接消费。

#### 7.1.5 不做的事

- **小程序端不做流程构建器**：拖拽画布在小程序体验差且无必要，构建仍由 PC 端 FlowBuilder 承担；
- **不引入 Vue Flow**：小程序无 DOM，画布类库不可用；
- **不存本地草稿**：小程序 localStorage（`wx.setStorageSync`）语义不同，且小程序端只读不需要草稿。

#### 7.1.6 风险与对策

| 风险 | 对策 |
| --- | --- |
| OSS 域名未加入小程序 request/downloadFile 合法域名 | 在小程序后台配置 OSS 域名（HTTPS） |
| 流程文件较大首次加载慢 | 文件预计 <50KB；可加 loading 态，必要时小程序端缓存已下载流程 |
| 图片预览体验 | 用 `wx.previewImage` 支持双指缩放，优于 H5 的 el-image |
| flowCore.js 双端同步漂移 | 抽包后用 npm/git submodule 共享，或 CI 校验文件 hash |

## 8. 风险与对策

| 风险              | 对策                                      |
| --------------- | --------------------------------------- |
| 用户画出无法到达的节点/死循环 | 保存前强制校验（见 3.3-5），校验报告逐项列出可点击定位          |
| JSON 手工改动导致损坏   | 导入时严格 schema 校验 + version 检查，失败给出具体字段错误 |
| 大流程画布性能         | 节点量级预计 <100，Vue Flow 虚拟化足够；无需额外优化       |
| 老数据无流程          | 流程是增量能力，原图文模式保持不变，互不影响                  |
